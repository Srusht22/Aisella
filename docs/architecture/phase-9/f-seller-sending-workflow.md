# F. Seller-controlled sending workflow

## 1. The rule

**No message reaches a customer unless a seller with `messages.send` authorized that exact text, in that conversation, at that moment.**
- The AI may propose text and prepare unapproved order drafts. It cannot send, schedule, approve or authorize.
- There is no auto-send, no scheduled send and no bulk send in Phase 9 (BR-47, D-06).
- Order confirmations are sendable only for an **approved** order (BR-04), and only by the same explicit action. A confirmation is never queued by an approval event, a status change or the AI: only the seller's Send creates it (owner condition 4).

## 2. States

```
compose ──Send (seller)──► queued ──claimed──► sending ──► sent ──► delivered ──► read
                             │                   │   └──► failed (permanent: reason shown; seller may edit and send again)
                             │                   └──────► unknown (never auto-resent; reconcile, then seller decides)
                             └──Cancel (seller, only while queued)──► cancelled
```

| State | Shown as (en) | Seller can |
|---|---|---|
| queued / sending | "Sending…" | Cancel while queued |
| sent | "Sent" | — |
| delivered / read | "Delivered" / "Read", where the channel reports it | — |
| failed | "Not sent: {reason}". Reasons: reply window closed, customer unavailable, connection needs attention, try again later. | Edit and send again (a new authorization) |
| unknown | "Sending status unknown" | Check later / Send again (confirmed) |

Sorani and Arabic texts follow the Phase 4 localization rules and get native review.

## 3. Reducing rubber-stamping

The unsolved risk is the seller tapping Send on a suggestion with a non-numeric promise ([Phase 8.5 H §4](../../implementation/phase-8.5/h-validation-gates-and-review.md#4-open-risk-non-numeric-fabricated-promises-not-solved)). Live sending makes it faster to approve without reading. Design controls:

1. **The suggestion is never in the send field by default.** The seller taps **"Use this reply"**, which copies it into the composer, where it is editable. The Send button is the composer's, not the suggestion card's. That is two deliberate actions.
2. **The composer shows the origin.** "Written by the assistant: check before sending" stays visible while the text is AI-originated and unedited. The facts used are listed under it.
3. **Held or escalated suggestions cannot be used for sending.** A holding reply can be used, because it says only that the owner will reply.
4. **No send from notifications** and no "send all".
5. **A confirmation step for order-related text.** If the conversation's intent is `place_order` or `order_status` and the text did not come from the server's order-confirmation template, the Send button asks once: "This message is about an order. Nothing is confirmed until you approve the order. Send?"
6. **Order confirmations** are generated by the server from the approved order (BR-04) and sent through the same Send action.

These reduce, but do not remove, the risk. The evaluation gate (Phase 8.5 G1 / G2) still applies before pilot sellers use live sending.

## 4. Server checks in `api.send_message`

| Check | Error |
|---|---|
| Signed-in end user, store member with `messages.send` | `FORBIDDEN` |
| Conversation belongs to the store, is live, and its connection is `connected` | `NOT_FOUND` / `CHANNEL_NOT_CONNECTED` |
| Contact not blocked | `CONTACT_BLOCKED` |
| Reply window open, or an allowed human-agent tag applies (only after the platform approves that permission, and only for human-authored replies) | `REPLY_WINDOW_CLOSED`, with the time it closed |
| Text 1 to the channel's maximum length (Instagram 1,000 characters [verify]; WhatsApp 4,096) | `VALIDATION_FAILED` |
| `kind = order_confirmation` ⇒ the order is in this conversation and `approved` or later, and the text is the server-generated one | `ORDER_NOT_APPROVED` |
| Store send rate | `RATE_LIMITED` |
| Idempotency key | Replay returns the same request |
| AI actor or worker roles | Cannot execute (no grant) |

The function stores the text exactly as authorized, its SHA-256, and whether it came from a suggestion unedited, edited, or not at all. **The sender sends that stored text and nothing else.**

**Exact-text guarantee (owner condition 3):**
1. `send_requests` stores the authorized text's SHA-256 next to the message, which is immutable once queued. The database refuses updates to the body of a `seller_sent` message.
2. `api.channel_claim_send` returns the stored text and its hash.
3. `channel-send` recomputes the SHA-256 of the exact string it is about to submit. On any mismatch it **does not call the provider** and fails the request with `TEXT_INTEGRITY`.
4. The adapter submits the string unmodified: no trimming, templating, signature or translation.
5. A test asserts that the provider stub received byte-identical text, including Sorani and Arabic.

## 5. Reply windows

- **Instagram and Messenger:** 24 h from the customer's last message. The composer shows "Reply window closes in 3 h". After it closes, Send is disabled with an explanation.
- **WhatsApp:** 24 h. Outside it, only approved templates can be sent. Phase 9 sends **no templates** (no marketing, no cost). A closed window means "Ask the customer to message you again" or using the phone.
- **Human Agent tag (Meta): deferred to Phase 9b by owner decision.** Phase 9 never sends with a tag. In 9b it would need the permission approved by Meta, be allowed only for seller-written text, and be limited to the 7 days in the official docs (I I4).

## 6. The manual paths stay

- Copy and "I sent this" (Phase 8) remain for imported conversations and for any live conversation where sending fails.
- A seller can always reply from the platform's own app. Echoes of those messages appear in the conversation as "Sent from Instagram", with origin `seller_external`, where the platform reports echoes.
